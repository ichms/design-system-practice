# 디자인 시스템 다시 생각해보기 (Toss Tech)

> 출처: https://toss.tech/article/rethinking-design-system
> 핵심 주장: 디자인 시스템은 "팀을 멈추게 하는 울타리"가 아닌 "팀을 지키는 가드레일"이어야 한다.

---

## 1. 문제 인식: 시스템이 경직될수록 우회가 발생한다

디자인 시스템이 성장하면서 역설적으로 사용하기 어려워지는 현상이 생긴다. 팀은 시스템의 제약을 피해 스스로 해결하기 시작한다.

**우회의 대표적인 패턴:**

- Figma 컴포넌트를 **detach**해서 직접 수정
- 디자인 시스템 패키지를 **fork**해서 로컬에서 변경

이 행동은 "일탈"이 아니다. **공급자가 수요를 제때 충족하지 못했다는 설계 부족의 신호**다.

> "우회로를 막는 통제보다, 우회할 이유를 줄이는 설계가 더 중요하다."

---

## 2. 패러다임 전환: 통제 → 유연한 확장

디자인 시스템을 **하나의 제품**으로 봐야 한다. 제품은 수요에 맞게 설계되어야 하고, 메이커(사용자)의 니즈가 예측 범위를 벗어나더라도 대응할 수 있어야 한다.

| 기존 관점          | 전환 후 관점                    |
| ------------------ | ------------------------------- |
| 일관성을 위한 통제 | 자율성을 존중하는 제약          |
| 예외를 막는다      | 예외를 수용할 수 있는 구조      |
| 컴포넌트 제공      | 확장 지점(extension point) 제공 |

---

## 3. 핵심 해결책: 컴포넌트 API 설계 패턴

### 3-1. Flat 패턴

내부 구조를 감추고 모든 변형을 props로 제공한다.

```tsx
<Button variant="primary" size="large" iconLeft="check" disabled />
```

- **장점**: 사용이 직관적이고 진입 장벽이 낮다
- **단점**: props가 끝없이 늘어나고, 예측하지 못한 요구에 대응 불가

---

### 3-2. Compound 패턴

하위 컴포넌트를 직접 조합하도록 구조를 노출한다.

```tsx
<Button>
  <Button.Icon name="check" />
  <Button.Label>확인</Button.Label>
</Button>
```

- **장점**: 확장성과 유연성이 높고, 코드 레벨에서 확장 지점이 자연스럽게 열린다
- **단점**: 사용자의 구현 난이도와 코드량이 증가한다

---

### 3-3. 하이브리드 전략 (TDS의 해결책)

"어떤 패턴이 옳은가"가 아니라 **"언제 어떤 선택이 적절한가"** 에 집중한다.

```
단순하고 자주 쓰는 케이스   →  Flat API
복잡하고 변형이 잦은 케이스  →  Compound API
```

**핵심 구현 아이디어**: Flat API를 Compound의 미리 조립된 케이스로 구현하면,
하나의 primitive로 관리하면서 두 인터페이스를 동시에 제공할 수 있다.

```tsx
// Flat (내부적으로는 Compound를 조합한 결과)
<Button variant="primary">확인</Button>

// Compound (같은 primitive 기반, 직접 조합)
<Button.Root variant="primary">
  <Button.Icon name="check" />
  <Button.Label>확인</Button.Label>
</Button.Root>
```

---

## 4. 제약의 역설

> 너무 경직된 제약은 시스템 사용을 저해하고, 결국 일관성이라는 가치 자체를 무너뜨린다.

강한 통제 → 우회 발생 → 파편화 → 일관성 붕괴의 악순환.
적절한 유연성 → 우회 필요 감소 → 시스템 내에서 해결 → 일관성 유지.

---

## 5. 결론

규모가 커질수록 메이커의 니즈는 다양해진다. 필요한 것은 더 강한 통제가 아니라,
**메이커가 제품 문제를 시스템 안에서 풀 수 있게 돕는 유연한 설계**다.

- "금지"와 "규칙 강화" 대신 선택지를 제공한다
- 자율성을 존중하는 구조가 궁극적으로 일관성과 효율성을 모두 달성한다
- 디자인 시스템 팀은 **컴포넌트 제공자**가 아니라 **플랫폼 설계자**로 역할이 바뀐다

# 디자인 시스템이 처음인 디자이너를 위한 기초 가이드 (요즘IT)

> 출처: https://yozm.wishket.com/magazine/detail/3338/
> 핵심 주장: 디자인 시스템은 완벽한 구조를 설계하는 일이 아니라, "우리 팀이 처한 문제를 해결하는" 반복적인 과정이다.

---

## 1. 문제 인식: 주니어 디자이너가 겪는 막막함

- "컴포넌트 만드는 법은 아는데, 어떻게 만들어야 잘 만드는 건지 모르겠다"
- 기술적 방법론은 많지만 실무 적용 가이드가 부족하다
- Material Design 같은 참고 자료는 너무 복잡하거나 추상적이다

---

## 2. 디자인 시스템 구축 4단계

### 2-1. 패턴 수집

먼저 제품 전체를 탐색하며 보이는 UI를 한 곳에 모은다.
"Figma에서 컴포넌트를 만드는 것"이 아니라, **무의식적으로 형성된 규칙을 발견하는 작업**이다.

---

### 2-2. 케이스 정리

수집한 UI를 종류별로 분류하고 세부 분류를 진행한다.

> **핵심 원칙: UI는 형태가 아닌 목적이 중요하다.**

형태는 서비스마다 달라도, 기능(목적)은 동일하다. 기능 중심으로 분류해야 다른 서비스와 비교하고 학습할 수 있다.

---

### 2-3. 논의하고 통합

개발자, 다른 디자이너와 함께 UI를 논의한다. "시스템화"는 반복되는 UI 코드를 템플릿화하는 것과 같다.

**트레이드오프 인식:**

| 선택지 수 | 속도 | 디자인 완성도 |
| --------- | ---- | ------------- |
| 적다      | 빠름 | 낮음          |
| 많다      | 느림 | 높음          |

정답은 없다. 팀 상황에 맞는 **타협점**을 찾는 것이 핵심이다.

---

### 2-4. 문서로 남기기

> "암묵적인 규칙들을 명시적으로 문서화하는 것이 핵심이다."

문서 작성 순서:

1. UI 이름 / 정의
2. 배치 규칙
3. 사용 사례 / 미사용 사례

"이렇게 쓰는 걸 권장한다", "이렇게는 쓰지 말자" 수준으로도 충분하다.

---

## 3. 결론

- 처음부터 완벽한 시스템을 만들려 하지 말 것
- **작게 쪼개서 천천히 정리**하는 과정을 반복한다
- 디자인 시스템도 제품이다 — 사용자가 외부가 아닌 사내에 있을 뿐, **꾸준히 개선**해야 한다

# 유연한 디자인 시스템을 위한 3단계 토큰 구조 (LINE Corp)

> 출처: https://techblog.lycorp.co.jp/ko/a-flexible-design-system-using-3-tier-tokens
> 핵심 주장: Figma Variables와 코드를 동일한 3단계 토큰 구조로 연결하면, 소규모 팀도 유연하고 일관된 디자인 시스템을 운영할 수 있다.

---

## 1. 문제 인식: 디자인 시스템 도입의 현실적 어려움

세 가지 구조적 문제가 도입을 막는다:

| 문제              | 내용                                                                   |
| ----------------- | ---------------------------------------------------------------------- |
| **개발과의 단절** | 디자인은 통일해도 각 팀의 코드는 따로 돌아가 전체 효율이 오르지 않는다 |
| **초기 설정**     | 기본 컴포넌트의 범위를 어디까지 잡아야 할지 기준이 없다                |
| **유지 보수**     | 컴포넌트가 많아질수록 갱신·수정 리소스가 폭증한다                      |

이 글은 **"개발과의 단절"과 "유지 보수"** 두 문제를 어떻게 해결했는지 다룬다.

---

## 2. 구조 선택: Figma + Storybook + HeadlessUI

**Figma → 토큰 → 코드** 흐름으로 리소스를 일원화한다.

### HeadlessUI를 산출물로 선택한 이유

HeadlessUI는 스타일 없이 기능(인터랙션·상태값)만 제공하는 라이브러리다.

| 비교 대상                   | 기술 지원 | 커스터마이징 |
| --------------------------- | --------- | ------------ |
| Ant Design 등 UI 라이브러리 | 높음      | 어려움       |
| **HeadlessUI**              | **중간**  | **쉬움**     |
| 커스텀 CSS                  | 낮음      | 완전 자유    |

- 외부 라이브러리는 기존 디자인이 박혀있어 커스터마이징이 어렵다
- HeadlessUI는 드롭다운 열기/닫기, hover 인터랙션 같은 기본 동작만 제공하고 스타일은 열어둔다

---

## 3. 핵심: 3단계 토큰 구조

```
Primitive 토큰
  └─ Semantic 토큰
        └─ Component-specific 토큰
```

### 3-1. Primitive 토큰 — 원시값

가장 하위 계층. 색상값·크기값 등 기본 단위만 보유한다.

```
명명 규칙: {색상 또는 크기}-{위계}
예시: zinc-100, radius-200
```

### 3-2. Semantic 토큰 — 맥락 부여

Primitive 토큰을 값으로 가지며, Component-specific이 적용되지 않은 모든 화면 요소에 사용한다.

```
명명 규칙: {컴포넌트 구조}-{위계}
예시: text-neutral-primary, fg-neutral-primary
```

### 3-3. Component-specific 토큰 — 컴포넌트 전용

사용처가 가장 구체적으로 한정된 계층. Semantic 또는 Primitive를 값으로 가진다.

```
명명 규칙: {컴포넌트명}-{위계}-{컴포넌트 구조}-{상태값}
예시: button-primary-text-default
```

### 토큰 카테고리 (4가지)

모든 컴포넌트는 아래 요소로 이름을 구성한다:

- `Text` — 컴포넌트의 글자
- `Icon` — 컴포넌트의 아이콘
- `Border` — 컴포넌트의 외곽선
- `Fg` (foreground) — 컴포넌트의 면(面)

---

## 4. Figma Variables → 코드 연결

Figma와 코드에서 동일한 토큰 구조를 사용하되, 구분자만 다르다.

```
Figma Variables:  button/primary/text/default
코드 (CSS 변수): --button-primary-text-default
```

Figma에서는 **Collection + Mode**로 3단계 구조를 구현한다:

- `Semantic` Collection: Light / Dark 모드
- `Component` Collection: Neutral / Blue / Green / Orange 스타일
- `Radius` Collection: Small / Medium / Large

→ 세 Collection의 Mode 조합으로 **24가지 테마**를 전환할 수 있다.

---

## 5. 실용적 최적화 기법

### 5-1. 프로퍼티명 통일

Figma 컴포넌트 프로퍼티명과 Storybook 프로퍼티명을 일치시키면 디자이너·개발자 간 불필요한 커뮤니케이션이 줄어든다.

### 5-2. 상태값 최소화

Hover와 Disabled를 공통 규칙으로 도출해 opacity로 처리했다:

```
Hover    → opacity-80 적용
Disabled → opacity-50 적용
```

결과: `<button>` 컴포넌트의 색상 관련 토큰 수가 **6개 → 2개 (67% 감소)**.

---

## 6. 결과

ABC User Feedback 프로덕트에 적용한 결과:

- Figma 기준 컴포넌트 커버리지 **80% 이상** 달성
- **Detach 0건** — 시스템 안에서 모든 케이스를 해결

> "스타일이나 구조에 대한 고민을 덜고, 더 중요한 사용자 요구와 문제 해결에 집중할 수 있었다."
